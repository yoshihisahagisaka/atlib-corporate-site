## 4. 実施権限・承認情報の設計

実測前に、統括承認記録へ少なくとも次を残す。

1. 団体の正式名称、管理主体、完全なHTTPS URL、および対象ページ範囲。
2. 所有者または正当な管理権限者による公開設定確認の許可。第三者の紹介や同名団体情報だけでは足りない。
3. 実施者、実施日・時刻（JST）、失効時刻、接続上限、連絡先、緊急停止窓口。
4. URLに厳密に結び付けた一回限りの承認レコード。発行者、期限、状態、取消、消費監査を含める。

承認レコードはソース、CLI引数、平文環境変数、HTML、診断JSON、通常ログに入れない。将来の秘密管理基盤で保管し、消費はDNS解決前に原子的に行う。発行・保管・取消機能はPhase 2Dでは実装も実行もしない。

## 5. 実測時の安全条件（承認後にのみ適用）

| 制御 | 上限・扱い |
|---|---|
| URL | 承認済み完全HTTPS URLのみ。443番、認証情報なし。パス・クエリを含め厳密比較 |
| DNS | Web事前照合と接続前再照合で最大2回。明示メールドメインが承認された場合のみSPF/DMARC TXTを各1回。合計最大4回 |
| HTTPS | 1 URLにつきGET 1回。TCP/UDPポート探索、認証、フォーム送信、脆弱性試験、負荷試験を行わない |
| 同時実行数 | 1 |
| DNS時間上限 | 各照会5秒。タイムアウト・中断・失敗は `UNVERIFIED` とし、不存在と判定しない |
| HTTPS時間上限 | 15秒。AbortSignalで要求を中止し、再試行しない |
| 応答上限 | 1 MiB。超過時は中止し、本文を継続受信しない |
| IP/TLS | 公開IPのみ。DNS再照合、固定IPへの接続、接続先IP照合、SNI/Host一致、証明書検証を必須とする |
| リダイレクト | 自動追跡なし。応答の`Location`は記録して停止。別URLは別承認 |
| 実施時間帯 | 権限者が指定するJST時間帯のみ。未指定なら実施しない |
| 中止 | 承認失効・URL/IP/TLS不一致・リダイレクト・上限超過・タイムアウト・権限者からの中止要請で即時停止 |

Node.jsのDNS Promise APIは、開始済み照会そのものの確実な取消しを保証しない。Phase 2Cは待機と結果採用を中止するが、リゾルバー上の問い合わせが短時間残る可能性がある。この制約を権限者へ事前説明し、実行前に受容を得る。

## 6. 実施手順（承認後のみ）

1. 承認記録と対象URLを二者確認し、期限・未使用・実施者・時間帯を確認する。
2. ローカル隔離保管先を作成し、OSアクセス権を実施者と承認済みレビュー者に限定する。保管場所、保持期限、削除担当を記録する。
3. 承認ストアから対象URLに拘束した一回限りの能力を取得する。値を画面・ログへ出力しない。
4. Webの事前DNS照合、接続前再照合、公開IP・DNS再束縛検査を行う。不一致ならHTTPS接続前に停止する。
5. HTTPS GETを1回だけ実行し、TLS、HTTPヘッダー、上限、リダイレクトを確認する。明示承認済みのメールドメインがある場合だけTXT照会を行う。
6. JSON 2.0の `targetUrl`、`checkedAt`、`http`、`tls`、`dns`、`mailDomain` を作成する。メールドメイン未指定なら `mailDomain: null` とSPF/DMARC `UNVERIFIED` を保持する。
7. Phase 2Aの企業ID・診断実行ID・レポートIDで、企業情報、診断JSON、判定JSON、HTML、整合性JSONをローカル隔離保管する。保存後にSHA-256を検証する。
8. VS1の既存ルール・固定解説・HTMLテンプレートでレポートを生成する。HTMLをローカル閲覧し、PDFはブラウザ印刷ダイアログでのみ必要時に保存する。
9. 実行ログには時刻、実施者、対象URL、回数、結果コード、成果物ID、停止理由だけを記録する。承認情報、本文、不要な個人情報、秘密値は記録しない。

## 7. 取得情報・成果物・保存

取得対象は、1件の公開HTTPS応答の状態・指定ヘッダー、TLS証明書検証情報、明示メールドメインのSPF/DMARC TXT情報のみである。メール本文、アカウント情報、Cookie、認証情報、Webアプリケーションの操作結果は対象外である。

保存する成果物は `company.json`、`diagnosis.json`、`result.json`、`report.html`、`integrity.json` と実行メタデータである。Phase 2Aのローカル隔離ストアは相対パス逸脱・上書き・整合性不一致を拒否する。保管先の具体的な絶対パス、アクセス権、暗号化、保持期間、削除方法は未承認であり、実施前に統括決定が必要である。外部URL、メール、共有ドライブへの自動配布は行わない。

## 8. 検証・成功条件・失敗条件

| 区分 | 成功 | 失敗／停止 |
|---|---|---|
| 承認 | URL一致・期限内・未使用・実施者一致 | 不在、期限切れ、使用済み、URL不一致 |
| 接続前 | 公開IP、二回のDNS結果一致 | 私設/特殊用途IP、DNS失敗/時間切れ、再束縛 |
| TLS/HTTP | 証明書検証、接続先IP照合、1 MiB以内、時間内 | 検証失敗、IP不一致、上限超過、時間切れ、リダイレクト |
| メールDNS | 明示メールドメインのみを取得し、状態を正確に分類 | 未指定を推測、失敗・形式不正を`NO_RECORD`化 |
| 成果物 | JSON 2.0、企業URL一致、VS1再現可能な判定、SHA-256一致 | 入力不整合、保存失敗、破損、再現性不一致 |

取得失敗・形式不正・未確認は「設定なし」または「安全」として利用者向けに表示しない。判定不能は既存VS1の内部証跡として扱い、ルール・文章・デザインは変更しない。

## 9. 統括承認が必要な事項と STOP 条件

以下をすべて満たすまでSTOPする。

1. 対象団体の正式名称、管理主体、完全な対象URL、対象範囲の確定。
2. 権限者による明示的な調査許可、JST実施時間帯、連絡先・中止窓口。
3. 一回限りの承認レコードの安全な発行・保管・取消・監査方法。
4. メールドメインを実施するか否かの明示判断。未指定ならメールDNSは実施しない。
5. 保存先、アクセス権、保持期間、削除責任者。
6. Node DNSの未完了照会リスク、DNS/IP拘束、TLS検証、回数上限の受容。

上記の承認前に、実DNS/TLS/HTTPS、実サイト診断、GCP・Production変更、PowerShell v2変更、メール送信、公開URL発行、外部配布を行わない。
