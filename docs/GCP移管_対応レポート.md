# atLIBコーポレートサイト GCP移管 対応レポート

最終更新: 2026-07-29
対象: `www.atlib.jp`（コーポレートサイト）・`recruit.atlib.jp`（採用サイト）
対応者: 萩坂佳寿

本レポートは、Claude Code（VSCode拡張）を使いながら、外部ホスティング上にあったatLIBのコーポレートサイト・採用サイトをGCPへ移管した一連の対応を、**自分が何を判断し、何を実際に手を動かして対応したか**という視点でまとめたもの。ツール側の実装詳細ではなく、意思決定の経緯と実作業の記録に重点を置く。

---

## 0. 前段：MSPプロジェクトにおける社内向けWebサーバー構築（2026年7月）

今回のコーポレートサイト移管に先立ち、同じくClaude Code（VSCode拡張）を使い、MSPプロジェクト（atLIB InfraVision、Zabbix監視基盤）向けの社内向けWebサーバー構築にも取り組んでいた。この時の判断・経験が今回の移管作業の土台になっている。

- **発端**: `msp-frontend-server`（レポートツール）・`zabbix-server`（Zabbix Web UI）に、テレワーク中の社員も拠点を問わず安全にアクセスできるようにしたいという要望からスタート。
- VSCode上のClaude CodeのPlanモードを使って構築方針を計画。GCP上に**HTTPS Load Balancer**を新設し、両サーバーをバックエンドとしてぶら下げる構成を設計した。
- 認証方式は、IPアドレスによるアローリストではなく**Cloud IAP（Identity-Aware Proxy）**を採用する判断を自分で下した（2026-07-04決定）。テレワーク環境ではアクセス元IPを固定できないため、Google Workspaceアカウント（`@atlib.jp`ドメイン）による認証の方が実態に即していると判断した。
- LB用の固定IPを確保し、DNS（`topology.zabbix.atlib.jp`・`zabbix-admin.atlib.jp`）をVMの外部IP直指定からLB経由に切り替え、IAPを有効化。あわせてファイアウォールもLB・ヘルスチェック専用のIPレンジのみに絞り込み、VMへの直接アクセスを遮断する対応まで行った。
- 概算コスト（LB用転送ルール分で月$18〜20程度の固定費増）も踏まえた上で承認・実施した。

**今回のコーポレートサイト移管との違い**: 上記のMSPプロジェクトの構成は、あくまで**社内スタッフ限定**のツールを想定しており、IAP認証で「ログインしていない人はそもそも中身を見せない」という設計だった。一方、今回のコーポレートサイト・採用サイトは**一般公開が前提**のため、IAPのような認証レイヤーを挟むと一般の訪問者がアクセスできなくなってしまう。そのため今回は認証は設けず、代わりにCloud Runのingress設定（`internal-and-cloud-load-balancing`）でLB経由以外の直接アクセスのみを遮断する構成を選んだ。「LB配下にサーバーを配置する」という骨格は共通しているが、**「誰を通すか」という設計思想は正反対**（IAPで絞り込む・vs・誰でも見られるようにしつつ抜け道だけ塞ぐ）になっている点が、今回の技術選定における重要な判断ポイントだった。

## 1. 移管の背景・要件定義

- 旧サイトは他社（外部の制作・保守会社）が管理する**Xサーバー**上にホスティングされていた。**この契約が終了することに伴い**、自社で管理できるGCP上へ移管する必要が生じたのが今回の対応のきっかけ。
- HTMLファイル一式は旧サイトから取得済みの状態からスタートし、「コーポレートサイトをGCP上に移管したい」という要望を提示。ドメイン自体はGoogle Workspace経由のSquarespace Domainsで管理していることを共有した。
- 配信方式の検討は「コスト・セキュリティ・SEO・AIO（AI検索対応）を総合して提案してよい」と方針決定を委任しつつ、以下は自分で判断・指定した。
  - GCPプロジェクトは**新規作成**（既存の社内MSP基盤とは分離し、課金・IAM・障害影響範囲を独立させる。外部業者依存だった旧体制から、自社で完結して管理できる体制への移行という意図も含む）
  - お問い合わせフォームには**サーバー処理が必要**（完全静的では不十分）という要件を明確化

## 2. インフラ方式に関する技術的な指摘

- 実際のSquarespace DNS管理画面のスクリーンショットを提示し、**「＠のAレコード変更だけで対応できるのかな？」**と質問。この一言が、Cloud Runの「ドメインマッピング」機能はapex（wwwなし）ドメインに対応していないという誤った前提を洗い出すきっかけになった。
- 調査の結果、Cloud Runのドメインマッピング自体がGoogle公式にPreview（本番非推奨）と明記されていることが判明したのを受け、**「本番向け構成優先」**を選択。Global External Application Load Balancer + Serverless NEGという、より手間のかかるが正式サポートされた構成を自分の判断で採用した。

## 3. 移管スコープの拡大判断

- 作業中に採用サイト（`recruit.atlib.jp`）が同一フォルダ内に同居していることが判明。**「recruitも同時に移管する」**と、スコープを自分の判断で拡大した。
- 問い合わせフォームの内部実装（PHPセッション依存の確認画面フロー）をサーバーレス環境向けにステートレスな方式へ作り直す方針についても、内容を理解した上で承認した。

## 4. GCPリソース作成の承認

- 新規GCPプロジェクト`atlib-corporate-site`の作成、および自社の請求先アカウントへのリンクを承認。
- 旧サイト（Xサーバー）のHTMLファイルの実際の格納場所（`G:\マイドライブ\website\260610_atLIB_HTML`）を提供し、実装の材料とした。

## 5. DNS切り替え作業（複数回、すべて自分で実施）

Squarespaceのドメイン管理画面を自分で操作し、以下を実施した。

1. **1回目の切り替え**: `@`（atlib.jp）と`recruit`のAレコードを、旧Xサーバーの向き先から、新しく用意したLBの固定IP（`136.69.71.191`）へ変更。
2. **証明書検証中の不整合に気づき、再点検を要求**: hostsファイルでの動作確認中、証明書の発行元が想定と異なる（Let's Encrypt表示＝まだ旧Xサーバー側を見ている状態）ことに気づき、**「本当に時間だけの問題？設計・設定など間違いないか再度確認して」**と、単純な時間待ちの説明を鵜呑みにせず設定全体の再監査を指示。この指摘が、後述のCloud Run側の認可設定漏れ（403エラー）の発見・修正につながった。
3. **ダウンタイムリスクを踏まえた判断**: 証明書のACTIVE化を待つ間、一部の訪問者がサイトにアクセスできなくなるリスクがあることを理解した上で、**一旦DNSを旧Xサーバー側へ戻す**判断を実施。
4. **再切り替え**: リスクを許容の上で、改めてDNSを新IPへ切り替え。
5. 状況確認の頻度についても**「もう少し短いスパンで確認して」**と、自分の希望するペースを明確に指示した。
6. 最終的なDNS設定内容（`@`・`recruit`のAレコード、`www`・`www.recruit`のCNAME）をスクリーンショットで再確認し、意図通りであることを自分の目で確認した。

## 6. メール送信設定に関する方針転換と実作業

お問い合わせフォームのメール送信元アドレスの検討では、複数回の方針転換を主導した。

1. 当初案の送信元候補`noreply@atlib.jp`について、**「メーリングリストであり個人アカウントとしてログインできない」**という制約を指摘。
2. 代替として提示された個人アドレス（`yoshihisa.hagisaka@atlib.jp`）の直接使用は、**「個人アドレス以外で送る方法ないの？」**と一度却下し、業務上ふさわしい送信元アドレスにこだわった。
3. 最終的に「既存アカウントにエイリアスを追加する」案を採用し、**`system@atlib.jp`**というエイリアス名を自分で指定。
4. **Google Workspace管理コンソールを自分で操作し**、`yoshihisa.hagisaka@atlib.jp`アカウントに`system@atlib.jp`エイリアスを追加。
5. 同アカウントで2段階認証を有効化し、**アプリパスワードを自分で発行**して提供した。

## 7. 本番環境での実地テスト

- 実際にブラウザから`www.atlib.jp`のお問い合わせフォームを操作し、初回はメール送信エラー画面のスクリーンショットを共有して不具合を報告（この時点ではSMTP認証情報が未設定だったため想定通りのエラー）。
- 修正反映後、改めて自分でフォーム送信をテストし、メール受信を確認した上で**「メールフォーム確認OK」**と結果を報告。
- 移管完了・旧Xサーバーとの契約終了を見据え、旧サイトのクローズについても自分から意思決定に着手した。

## 9. 開発基盤について：Claude Code × VSCode × Git × GCPの連携

今回の一連の作業を支えた開発環境の仕組みについても、社内共有の観点でまとめておく。

- **Claudeの利用方法**: 「Claude Code」というAIエージェントをVSCodeの拡張機能として利用した。チャット形式で要望を伝えると、コードの生成だけでなく、ターミナルコマンドの実行・ファイルの読み書き・実際の動作確認までを一気通貫で行ってくれる。影響の大きい作業（GCPリソース作成、DNS変更など）の前には、実行せず提案内容だけを確認する「Planモード」に切り替え、内容を承認してから初めて実作業に移る、という進め方を意図的に採った。
- **VSCodeとの連携方法**: Claude CodeはVSCode上で直接動作するため、開いているファイルや選択中のテキストといったエディタ上のコンテキストを自動的に把握する。コード編集・統合ターミナル（PowerShell／Bash両方を状況に応じて使い分け）でのコマンド実行が同じ画面内で完結するため、別途ブラウザやSSHクライアントを行き来する手間がない。
- **Gitでの管理**: 今回作成した`corporate-site/`一式は、`msp-customer-portal`や`zabbixserver`など社内の既存プロジェクトと同じGitリポジトリ内に配置し、資産を一元管理している。なお本レポート作成時点ではまだコミットしておらず（`git status`で未追跡の状態）、コミットのタイミングは別途判断する運用とした（Claude Codeは明示的に指示しない限り勝手にコミットしない設定で運用しており、不用意な変更履歴を残さないようにしている）。
- **GCPとの連携方法**: ローカル環境で`gcloud` CLIが認証済みだったため、Claude Codeがそのままターミナル経由でGCPを操作できた。プロジェクト作成・請求先アカウントのリンク・Cloud Runへのデプロイ・Load Balancer一式（固定IP・証明書・NEG・バックエンドサービス・URLマップ・プロキシ・転送ルール）の構築・Secret Managerへの認証情報登録・IAM権限設定まで、GCPコンソールを手動でクリックする必要がなく、すべてコマンドラインから完結した。

### 特に共有したい点：VSCode（Claude Code）がサーバー構築・テスト・デプロイまで一貫して担えること

- コード（Express/TypeScriptサーバー）を書くだけでなく、ローカルで実際に起動してAPIの動作確認（フォーム送信のE2Eテスト、なりすまし防止の検証など）まで自動で行った。
- Dockerイメージのビルド・Cloud Runへのデプロイ・Load Balancer／証明書／DNS周りの構築、さらに本番運用中に発生した不具合（SSL証明書の検証停滞、IAM権限不足による403エラーなど）の切り分けと修正までを、実際の本番環境に対してコマンドラインから直接実行し、その都度結果を報告する形で進められた。
- 「要件を伝える → 計画を確認する → 実装・構築を任せる → 本番で動作確認する」というサイクルを、担当者はエディタとチャットの中だけで完結できる。

これは、従来インフラエンジニアとアプリケーションエンジニアで役割が分かれていた領域を、一人が対話形式で横断的にカバーできることを意味する。少人数のIT体制であるatLIBにとって、今後の開発・運用の進め方を広げる技術として特に共有しておきたい。

## まとめ: 対応の要点

| 局面 | 自分が下した主な判断・実施した作業 |
|---|---|
| 前段（MSPプロジェクト） | 社内向けツールのLB+Cloud IAP構成をPlanモードで設計・判断。今回の外部公開サイトでは認証方式（IAPなし・ingress制限のみ）を意図的に変えた |
| 背景 | 外部業者管理のXサーバーの契約終了を受け、自社GCPへの移管を主導 |
| 方式選定 | 本番向け構成（LB+Serverless NEG）を優先する判断／apex対応の技術的な疑問を提起し設計ミスを未然に発見 |
| スコープ | 採用サイト(recruit.atlib.jp)を移管対象に追加する判断 |
| インフラ承認 | 新規GCPプロジェクト作成・請求先リンクの承認 |
| DNS切替 | Squarespace管理画面での実操作（複数回）、リスクを踏まえた一時ロールバック判断 |
| 品質管理 | 「時間の問題と決めつけず設定を再点検してほしい」という指摘により設定不備を発見する契機を作った |
| メール送信 | 送信元アドレスの業務要件（個人名を出さない）を明確化し、エイリアス方式を選定・Workspace管理コンソールでの実設定・アプリパスワード発行 |
| 本番検証 | 実際のフォーム操作によるE2Eテストと受信確認 |
| 運用移行 | 旧Xサーバーとの契約終了に合わせた旧サイトクローズの意思決定着手 |
| 解析強化 | GA4データストリーム追加・Microsoft Clarity導入の要件定義とアカウント側の実設定 |

一連の対応を通じて、外部業者依存だった旧サイト体制からの脱却を主導し、インフラの技術選定・リスク判断・外部サービス（Google Workspace、Google Analytics、Microsoft Clarity）のアカウント操作・本番環境での実地検証を、要所要所で自ら主導して完遂した。
